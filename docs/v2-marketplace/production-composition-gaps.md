[`currentMarketplaceRelease()`](../../broker/src/v4/marketplace/durable-release.mjs) still lists all five blockers. Release validation checks evidence-digest shape; it does not itself verify that four digest strings describe reviewed artifacts. The eventual constructor must bind actual reviewed source, screening, policy/skills and database evidence.

## Collection security: reusable observations are not a clearance

[`inspectContract({client,contract})`](../../broker/src/v4/skill-forge/research-tools.mjs) reads code/hash, ERC165 responses, EIP-1967 implementation/beacon slots and minimal-proxy shape. Its explicit verdict is `NOT_A_SECURITY_CLEARANCE`; interfaces can lie and nonstandard proxies can evade those slots. [`createCollectionEvidenceV1`](../../broker/src/v4/skill-forge/collection-evidence-v1.mjs) adds bounded metadata observations with client-level CCIP disabled, a closing canonical-header check, and `executable:false`. Neither grants marketplace `PASS`.

[`screenKnownSafeMint`](../../broker/src/v4/security-screen.mjs) verifies a known mint transaction against supplied negative hazard evidence and returns `PASSED`, not the marketplace's `PASS`. It does not discover or prove those facts. [`screenAutomatedSeaDropCandidate`](../../broker/src/discovery/automated-seadrop-screen.mjs) and [`attestAutomatedSeaDropCandidateLive`](../../broker/src/discovery/automated-seadrop-live-screen.mjs) provide useful patterns: fixed runtime/protocol pins, independent provider evidence, canonical observations and exact simulation. Their actual predicates require a reviewed SeaDrop clone and active zero-price mint; they are not a Seaport resale clearance. Other existing Scatter/HoodDrop screens likewise remain adapter-specific.

The agreed `screenCollection({collection,codeHash,anchor})` interface is sufficient for a narrow server-owned verifier that loads real reviewed collection evidence, rechecks it at the supplied anchor and returns `{status:'PASS',collection,codeHash}` only for that supported runtime. It can reject unknown/proxy collections without changing the HTTP or transaction interfaces. A code hash merely matching the hash just read from RPC is not independent safety evidence. The guard checks outer collection code hash, not arbitrary proxy implementation state; supporting mutable proxies can require further execution-time invariants and a separately reviewed contract/scope change. Do not silently promote an inspection report or the copied-chain test NFT into a production clearance.

## Policy and skills: exact available APIs and incompatibilities

The current JavaScript policy path is mint-specific:

- [`normalizePunkCollectingIntent` / `punkCollectingIntentHash`](../../broker/src/v4/collecting-intent.mjs) bind owner/Punk/wallet, ASK/ASSIST/AUTONOMOUS mode, mint price/gas/count limits, reserve and collection restrictions. [`matchV2Opportunity`](../../broker/src/v4/policy-matcher.mjs) consumes the mint-shaped [`normalizeV2Opportunity`](../../broker/src/v4/opportunity.mjs), with mint-stage/adapter identities and screening/simulation states.
- [`normalizeV4PunkPolicy` / `evaluateV4PunkOpportunity`](../../broker/src/v4/punk-policy.mjs) require automation-enabled mint policy and mint counters. [`evaluatePaidMint`](../../broker/src/control-center/paid-mint-policy.mjs) requires an active paid-mint authorization and per-mint/daily mint usage. [`normalizeArtMandate`](../../broker/src/mandate.mjs) and [`normalizeOwnerArtMandate`](../../broker/src/owner-art-mandate.mjs) also expose mint-specific economic controls.
- [`createMintResearchContextReader`](../../netlify/functions/_shared/v2-mint-research-context.mjs) is a useful authenticated data-access pattern: verified Agent authority, stored `broker_v2_strategies` hash/version/owner confirmation, canonical ownership history and verified usage. Its actual opportunity and accounting queries remain mint-specific.

Mapping a secondary purchase to a synthetic mint, treating an existing `FREE_ONLY` strategy as purchase permission, or setting missing screening/simulation flags to true would invent authority. Marketplace purchases spend price from the Agent while the owner pays gas; current mint matching often charges price plus gas against one wallet. The policy dependency is invoked before core's final gas estimate/simulation, so a wrapper cannot truthfully manufacture those completed results to satisfy a mint evaluator. It can constrain the supplied maximum fee budget and let the existing final core checks enforce actual fees, once that purchase policy has been defined.

There is genuine secondary-acquisition groundwork: [`GoghBrokerTypes`](../../contracts/src/GoghBrokerTypes.sol) defines `SECONDARY_BUY`, `AcquisitionIntent`, `PolicyConfig.maxSecondaryPurchasePrice`, daily/weekly spend and acquisition caps. [`BrokerPolicyModule`](../../contracts/src/BrokerPolicyModule.sol) exposes `policy`, `currencyPolicy`, `approvedAdapters`, `approvedMarketplaces`, `approvedCollections`, denial/selector checks, venue limits and `usage`; `validateAndConsume` enforces and updates acquisition usage. [`IGoghMarketplaceAdapter`](../../contracts/src/interfaces/IGoghMarketplaceAdapter.sol) defines deterministic venue execution, but the existing implementations under `contracts/src/adapters` are mint adapters.

That legacy policy is **not consumed** by the selected marketplace route. The pinned [`GoghPunkAgentAccount.executeBatch`](../../contracts/src/GoghPunkAgentAccount.sol) is current-owner execution; it does not call `BrokerPolicyModule`. The module consumption appears in the distinct [`GoghPunkAccountV1`](../../contracts/src/GoghPunkAccountV1.sol) acquisition path. Reading legacy limits alone would not make its usage counters include current Agent purchases. Replacing the agreed Agent batch with that path, installing a module, registering a new contract adapter or enabling protocol feature flags is a product/transaction scope change, not routine dependency wiring.

For equipped skills, reuse [`createProgressionReader`, `resolvePunkCapabilities` and `createSkillToolGate`](../../broker/src/v4/skill-forge/capability-resolver.mjs): they check pinned registry/progression code, current owner, slots, equipped keys, learned levels, registry availability/disable/deprecation, exact manifest/instruction hashes and declared tool identities. The result explicitly has `walletAuthority:'NONE'` and `requiresSeparateEconomicAuthorization:true`. [`loadResearchSkillCatalog`](../../broker/src/v4/skill-forge/research-runtime.mjs) checks implementation/dependency hashes but initially returns TESTING/unapproved packages. [`createV2McpResearch`](../../netlify/functions/_shared/v2-mcp-research.mjs) promotes only exact packages in the server release and brackets reads with [`readReviewedTrainingState` / `assertTrainingOwnerContinuity`](../../broker/src/v4/skill-forge/training-state.mjs).

The inspected [`robinhood-forge-training.json`](../../deployments/robinhood-forge-training.json) is an OWNER_CANARY for one owner and only Rarity Eye. Local Floor Hunter v1 and Market Scout v2 manifests declare MARKET_READ with no wallet/executor capabilities; Contract Detective declares CONTRACT_READ. Their staged implementation does not imply live registration, release inclusion, learning or equipment. No BUY_LISTINGS capability or automatic purchase permission should be invented. The exact required packages for owner-assisted purchase review must be specified separately. Existing progression readers choose their own latest anchor; a marketplace bridge needs explicit alignment or continuity verification against the supplied purchase anchor, rather than pretending unrelated snapshots are identical.
