## Native purchase reasoning

The listing normalizer accepts one exact ERC721 asset per order, fixed native consideration and full-open Seaport orders. It rejects partial/restricted orders, criteria, bundles, floating-point numeric inputs, mismatched source assets/prices, mixed ERC20/native payments and missing signatures/counters. Preparation recomputes each order hash with pinned Seaport, checks the seller counter/status/current token owner, enforces unique assets/order hashes and limits selection to five listings. Server-owned original records and authoritative policy/screen callbacks remain required trust boundaries; their conclusions must never come from the browser.

Each prepared batch contains exactly the selected Seaport fulfillments and a final stateless guard. The released Agent increments its state before batch calls and uses an execution reentrancy lock. The guard binds the original Punk owner, canonical account, expected next account state, token ownership, collection runtime, reserve, and deadline. Intervening account activity or insufficient post-purchase reserve reverts the entire batch. The implementation is not changed to allow approvals, delegatecalls, general signatures, or autonomous paid buying. Exact state checks can also reject collections that unexpectedly invoke receiver hooks; this fails closed rather than granting additional authority.

Native price is the sum of the exact signed consideration and exact per-call values. The Agent pays those prices; the owner funds the separate network fee. The selected sample never claims a verified collection floor. Receipt matching uses the exact saved calldata plus pinned Seaport order hashes, delivered ERC721 transfers, native consideration totals and historical recipient ownership. The three identified receipt/envelope defects require the fixes above.

Runtime equality alone does not prove arbitrary collection behavior or detect an unchanged upgradeable proxy's implementation/storage changes. The required authoritative collection screen must reject unsupported mutable or malicious behavior; this review does not turn a runtime hash into a universal safety certificate.

## WETH escrow and zone reasoning

Creation uses exact owner-funded ETH, wraps that amount, constructs the complete quantity-one WETH/NFT order internally, increments a funder nonce, and fixes the canonical Agent as recipient. A finite allowance tracks held WETH. The escrow has no generic execution method or Agent module permission. Its ERC1271 response is limited to known active digests, and full-restricted orders route actual settlement through its Seaport-only zone. Current-owner checks in the zone remain necessary because Seaport can cache signature validation.

The independent callback tests bypass a fresh signature check and still reject fulfillment after the copied Punk transfers. The zone checks exact offer amount/token, exact NFT collection, quantity, recipient and token ID for an item bid; criteria bids permit a resolved quantity-one token. Post-delivery ownership is required before `SETTLED`. Unauthenticated zone invocation and stale create nonces fail. The escrow's create/cancel/settle entry points use a reentrancy lock; zone callbacks authenticate the pinned protocol and perform static external ownership checks. No supported route for an arbitrary caller to skip the restricted zone or drain another active bid was demonstrated.

Original-funder cancellation remains available after ownership changes and does not transfer a predecessor's funds to the new Punk owner. The independent tests exercise pooled active/settled bids, a new-owner refund attempt, repeated cancellation, a criteria token resolution, recipient substitution and exact-token substitution. The silent terminal cancellation is on-chain idempotency working correctly; IMS-01 is the missing receipt-reader interpretation of that behavior.

**Ownership continuity is not solved.** The independent local test transfers the copied Punk away and back, then successfully fulfills the old bid. Current ownership becoming true again is sufficient for the existing zone. Public WETH activation requires a separately reviewed epoch or equivalent continuity design. Custom-zone acceptance by OpenSea and public order posting have not been independently established, and must not be inferred from successful Seaport settlement.

## Repair follow-up

The implementation author committed `8552edf18235ae9091616994d56a0c6ec27189d4`. Independent source review and local tests close IMS-01 through IMS-03:

- Cancellation review now captures the escrow runtime and immutable bid fields. Recovery reads the exact `bids(orderHash)` tuple at the receipt block, verifies funder, recipient, Punk, collection, token, price, salt, counter, timestamps, criteria flag and runtime hashes, and rechecks the canonical block after that work. `BID_CANCELLED` reports only the current receipt's refund. `BID_ALREADY_CANCELLED` and `BID_ALREADY_SETTLED` both return `refundedWethWei:'0'` and `refundInThisTransaction:false`. They do not claim NFT delivery from a cancellation receipt.
- Prepared transactions explicitly use legacy type `0x0`. Recovery rejects missing/unsupported type, absent/nonpositive gas values, higher gas price/limit, additional priority/max/blob fee fields, access lists or authorizations. A low mined effective price no longer hides another transaction envelope. Receipt gas used and effective price must be present, positive and within the actual transaction's bounds.
- Returned transaction hash and block identity must agree with the requested hash, receipt and canonical header before terminal interpretation. Unknown or missing receipt status now yields `RECEIPT_STATUS_UNAVAILABLE`; it cannot be mistaken for a confirmed revert and release a journal attempt.
