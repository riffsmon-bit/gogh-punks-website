# Staged signed fulfillment source review

Status: implementation and offline tests only. The adapter is not installed in production, and no live fulfillment POST, listing creation, approval, wallet request or public transaction was performed. A live eligible selected-order canary remains unproven. The existing blocked release remains unchanged.

## Server interface and retrieval boundary

`broker/src/v4/marketplace/opensea-fulfillment-listings.mjs` exports `createOpenSeaFulfillmentListingReader({ apiKey, fetchImpl = fetch, now = Date.now, timeoutMs = 8000, callTimeoutMs = 4000 })`, its bounds and a fixed-code error class. The returned `loadListings({ collection, orderHashes, anchor, wallet })` implements the extended trusted dependency. Root integration supplies `wallet` from the canonical Agent reads already performed by core preparation. Browser request fields remain selected hashes and exact budgets; the browser cannot choose this wallet, transport, endpoint, credential, protocol or returned order evidence.

The adapter requires a lowercase nonzero wallet address before making any API request. This is a shape and scope check, not an independent proof of the Agent's on-chain identity; that proof belongs to the calling core. It rejects the controlling collection and accepts one through five unique exact hashes. The optional-wallet change to the GET-only reader preserves its compatibility with the extended core interface and legacy callers.

Every lookup first retrieves the originals using the fixed Robinhood/canonical Seaport 1.6 exact-hash GET endpoint. Only after **all** selected originals pass validation does it call the documented fixed `POST https://api.opensea.io/api/v2/listings/fulfillment_data` endpoint. Each body contains only `listing:{hash,chain:'robinhood',protocol_address:canonicalSeaport}`, `fulfiller:{address:wallet}`, `recipient:wallet`, `units_to_fill:1`, and `include_optional_creator_fees:false`. This endpoint retrieves fulfillment data and signatures. It is distinct from order creation and blockchain broadcasting. [OpenSea fulfillment API](https://docs.opensea.io/reference/generate_listing_fulfillment_data_v2), [official SDK request construction](https://github.com/ProjectOpenSea/opensea-sdk/blob/main/src/orders/utils.ts).

This code has no signer, wallet client, broadcast/RPC method, approval operation, cancellation path, order-creation endpoint or provider-selected callback. Retrieval may vend a fulfillment signature, so it is not classified as universally free of offchain effects. OpenSea describes SignedZone cancellation guarantees as depending on whether a fulfillment signature was already vended. Restricted orders are rejected before this adapter calls that endpoint. [OpenSea cancellation semantics](https://docs.opensea.io/reference/cancel_order).

## Checks before signature vending

The GET batch must contain ACTIVE, remaining-quantity-one, fixed-price, full-open ERC721 listings. It verifies Robinhood, canonical Seaport, each exact selected hash, a noncontrolling selected collection, exact token identity, a seller other than the Agent, zero zone and zoneHash, and expiry beyond the maximum of anchor/server time plus 60 seconds. It requires one offered ERC721 and one through sixteen exact native-ETH consideration entries. All required fees and recipients are preserved; disabling optional creator fees does not remove required consideration.

Unsigned structural validation never substitutes a fake signature. It requires the original counter and all order components, normalizes supported representations without precision loss, then hashes the full Seaport `OrderComponents` and compares it to the selected identity. Decimal amounts remain strings. Exact hexadecimal salts, including padded uint256 values, are converted losslessly to decimal; safe integer representations are accepted only in the bounded documented response positions. Original GET counters require decimal strings. Missing fields, unsupported signatures already present in GET, imprecise numbers, duplicates, mismatched price, unsupported currencies, criteria, partial/restricted orders or changed components prevent every POST in that batch.

## Binding the returned signature and transaction description

The response must name `seaport1.6`, contain exactly one signed order, and include the documented transaction envelope. Every returned order parameter and counter must equal the validated GET original after lossless numeric normalization. The full order hash is recomputed. Signature bytes must have a supported 64/65-byte shape, match any signature already observed in GET, and equal the signature in the described call.

Only the exact `fulfillAdvancedOrder` name or its canonical full ABI signature is accepted. The transaction must target pinned Seaport on integer chain 4663 with the exact native consideration value; an optional hexadecimal value must agree. Its strict input shape requires the same order parameters, all required consideration entries, 1/1 numerator/denominator, empty criteria resolvers, empty extraData, zero fulfiller conduit and the server-derived Agent recipient. Unknown execution fields, raw wallet calldata, alternate functions, approvals and extra calls fail closed.

The adapter independently encodes the parsed description with the repository ABI, compares it byte-for-byte with the fixed call built from the GET original plus actual returned signature, and checks selector `0xe7acab24`. An optional attribution suffix must be exactly four hex bytes. It is recorded only in provenance and never appended to execution bytes. The provider documents this suffix as attribution metadata whose omission does not alter execution. [OpenSea transaction response schema](https://docs.opensea.io/reference/generate_listing_fulfillment_data_v2).

The result contains only the validated original listing, its actual returned signature, and immutable provenance. It never returns the API transaction for execution. Final validation calls the existing `normalizeNativeListing` with those actual signature bytes. The unchanged core then creates its own Seaport calls and purchase-guard batch. Provenance records both fixed endpoints, GET/POST response hashes, exact POST-body hash, wallet/order/chain/anchor, observation time, derived call digest, optional attribution metadata, `executionAuthority:'NONE'`, zero broadcasts/order creations and `signatureVending:'MAY_OCCUR'`. The API observation is explicitly latest-state, not block-pinned. Signature executability still requires the existing pinned Seaport simulation.

## Evidence, tests and counterexamples

The official SDK's captured native advanced-order response confirms the canonical function signature, decimal string consideration count inside call parameters, hexadecimal salt inside the returned order, separate signed-order array and optional attribution suffix. That captured Ethereum example has a restricted zone, nonempty extraData and nonzero fulfiller conduit; it is a counterexample this adapter deliberately rejects, not a supported live fixture. Its capture notes also report provider rejection of several placeholder fulfiller addresses. Acceptance of the canonical Agent contract as a live fulfiller remains unproven. [Official native fulfillment capture](https://github.com/ProjectOpenSea/opensea-sdk/blob/main/test/fixtures/fulfillment/advanced-order-native.json).

The local test fixture uses that documented wire structure with synthetic full-open Robinhood data and explicitly offline signature bytes. It does not copy a live signed order or claim cryptographic signature validity. Tests cover exact body construction, every required fee, selection-wide preflight before vending, original/returned/call parameter and signature substitution, counter and numeric precision, target/value/chain/function/recipient/conduit changes, extra fields/calls, attribution omission, maximum ten requests, sanitized provider errors, redirects/SSRF, oversize/invalid UTF-8/JSON, call and shared deadlines, late response cancellation, expiry and clock rollback. Reproduction:

```sh
node --test tests/marketplace-opensea-fulfillment-listings.test.mjs tests/marketplace-opensea-signed-listings.test.mjs
```

The combined suite passed 113 tests: 77 fulfillment cases and 36 GET cases. Each invocation permits at most five GETs followed by five POSTs, no retries, at most 65,536 streamed bytes per response, four seconds per call and eight seconds shared across both stages. Deadlines include stalled bodies and uncooperative injected fetch promises; late GET completion cannot initiate a POST.

Known limits: a basic/batch/match function, restricted zone, nonzero fulfiller conduit, additional response execution shape or unsupported original representation is rejected even if OpenSea itself could execute it. No deliberate mapping for those cases exists. Provider trading-account eligibility, a supported live full-open response, signature validity, chain state, collection safety, policy/skills, guard deployment and durable release approval remain separate requirements. Neither a well-shaped signed response nor these offline tests supplies those attestations.
