## Result

The original-NFT Forge stack is deployed and its recorded runtime hashes match two public RPC observations. **Rarity Eye v1 is the only registered skill, READY and available; Punk #93 has not learned or equipped it.** Three native research packages exist, while the requested ten skills are a mixture of reviewed research, unaccepted integration work and proposals. Neither registry status nor a catalog card grants spending authority.

The existing progression and research gates already enforce the essential learned/equipped/current-owner distinction. No replacement registry, progression system or upstream runtime is needed. General skill promotion remains blocked by individual acceptance work. Market Scout needs a separately versioned price/identity/freshness improvement before broader acceptance; its current reader cannot establish an executable order, collection floor or WETH bid. Rarity Eye remains explicitly sample research, separate from the frozen allocation used for starting slots.

## Market and rarity findings requiring coordinated scope

**M-01 — P2 current read-data defect; required before Market Scout promotion.** [market-reader.mjs](../../broker/src/v4/skill-forge/market-reader.mjs) validates `String(price.value)` after ordinary JSON parsing. An offline response containing raw JSON number `9007199254740993` produced string `9007199254740992`; precision was already lost. Valid decimal-string amounts retain exact precision, as the new test verifies. Reject non-string raw amounts (or adopt an explicitly reviewed lossless parser); use exact integer arithmetic and a deliberate amount bound. This does not enable spending today: Market Scout is unaccepted and results remain non-executable. Do not freeze the incorrect behavior in an acceptance test.

**M-02 — P2 required intelligence semantics before floor/order use.** The current result has `orderHash`, integer value, decimals, currency **label** and chain ID. It does not establish payment-token address/native identity, NFT contract/token ID per order, quantity/unit versus total price, expiry, order validity or remaining fill. Collection identity is checked on OpenSea's collection response; listing entries are only filtered by chain. A symbol such as ETH or WETH is not currency identity. `observedAt` is fetch completion time, not provider order time or quote expiry; pagination completeness, collection floor, cross-currency normalization, wash-trade/liquidity analysis and executable bids are not provided. The fixed GET host, redirect refusal, response-size/time bounds, explicit source and stripped transaction material are useful protections; preserve them.

Recommended implementation scope for M-01/M-02 is a **new versioned native market reader and Market Scout package**, separately assigned by the lead. Preserve v1 artifacts; add exact currency/asset identity, string amount/decimals, unit quantity, provider/source timestamp, request observation, expiry/validity and coverage fields with explicit unavailable values. A reference floor needs declared currency and dataset selection; it must never be inferred from the minimum of five mixed or incomplete listings. Add provider-error, malformed/unsafe-number, mixed-currency, wrong-order-asset, stale/expired, pagination and hostile-metadata tests before reviewed release acceptance. A purchase/bid adapter remains separate work, with its own policy, simulation and owner permission.

**R-01 — P2 limitation for broader rarity claims.** [research-tools.mjs](../../broker/src/v4/skill-forge/research-tools.mjs) uses inline base64 JSON tokenURI data, at one numbered block, for at most 50 token IDs. Public equipped API/MCP scope is exactly three distinct Punks including the selected Punk; numeric traits are explicitly interpreted as categorical. Ranking is `GOGH_INVERSE_TRAIT_FREQUENCY_V1`, competition ties and explicit missing traits, with `SAMPLE_ONLY` coverage and no price estimate. It is not OpenRarity. Metadata and ranking hashes bind the supplied tokens; the ranking's evidence hash alone does not bind algorithm/numeric mode, coverage completeness, source freshness or a collection-wide dataset. Outer result fields and pinned implementation supply some of that context. Research reads do not independently recheck their own metadata block for reorgs; the progression/owner checks protect authority, not a comprehensive data-finality claim.

A future rarity version needs dataset/algorithm/mode provenance, canonical block recheck, coverage/revealed-state handling and reproducibility tests. Changing the shared `research-tools.mjs` would invalidate **both** Contract Detective v1 and Rarity Eye v1 implementation hashes; avoid that implicit coupling by assigning new implementation/package versions. Frozen starting-slot allocation remains a separate reviewed artifact; sample results must not alter its root or issue slots.

**C-01 — P2 presentation/deployment evidence drift.** Historical docs claiming zero READY skills and the read manifest's paused note predate the selected deployment. The generic TESTING catalog is intentionally distinct from the accepted release, but UI/release summaries should explain that distinction. Coordinate a narrow display/documentation follow-up with the UI owner; do not promote all catalog cards or flip write flags to make status text agree. Extend the existing deployment audit in a separately assigned change if durable automated Forge code/state coverage is wanted; its current PASS is not itself that coverage.
